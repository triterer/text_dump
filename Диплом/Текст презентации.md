Сегодня я расскажу про разработку распределённой, документно-реляционной базы данных и методов её реализации
## Цели, задачи
Существует много видов баз данных, но не существует идеального варианта. Каждая обладает своими особенностями работы, сильными и слабыми сторонами. Поэтому для решения задачи реализации мультигранулярного файлового хранилища следует решить следующие задачи:
1. Проанализировать существующие решения файловых хранилищ и определить что в них не подходит для решения наших задач
2. Разработать алгоритмы с учётом оптимизации работы для поставленных задач
3. Верифицировать корректность работы алгоритмов при помощи математического аппарата
4. Разработать систему для проверки эффективности алгоритмов

## Актуальность
Такие требования выставляются для высоконагруженных бд по объеденённому управлению конфигураций и хранению метрик кластерных вычислений:
1. Возможность распределённо хранить документы формата JSON
2. Возможность обновлять из части не блокируя доступ к другим
3. Поддерживать транзакционность при изменении документов
4. Иметь возможность распределять нагрузку между разными серверами

## Минусы существующих решений
1. HADOOP
- ориентировани на OLAP
2. MongoDB
- Поддерживает блокировки только на уровне целых документов
3. FaunaDB
- Требует для всех операций синхронизации с центральным сервером

## Предлагаемые решения проектирование
Соответсвенно требуется разработать протокол СУБД которые будут отвечать всем заданным требованиям. В целом задача eventual consistency для документных БД уже решена, но для ACID пока есть потребность в новых решениях, так как протокол Calvin исползуемый в FaunaDB не подходит.  Поэтому для разработки протокола работы будут применятся математические модели Communicating Sequential Processes и Сетей Петри для проверки выполнения требований ACID и избегания состояния deadlock. Для реализации многоуровневой блокировки будет применятся Multi Granularity Lock.

## Предлагаемые решения реализация
А для реализации будет применятся язык программирования RUST, для взаимодействия компонентов между узлами библиотека tokio, а в качестве нижележащей системы локального хранения на каждом узле будет применятся ROCKSDB.
